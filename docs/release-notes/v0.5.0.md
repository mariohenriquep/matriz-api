# Matriz 0.5.0 — notas da versão (candidata)

> **Estado: versão candidata.** Passa a 0.5.0 final, com a tag `v0.5.0`, depois da validação do Ex. 6 da Ficha 05. Não é uma release de produção.

## Resumo

A 0.5.0 não traz funcionalidades novas para o utilizador. Esta versão prepara a Matriz para ser **construída, testada e executada de forma reproduzível**: a aplicação completa arranca com um comando (`docker compose up -d --build`) e cada alteração passa por uma pipeline de CI com testes, análise de segurança e de qualidade.

## Novidades

- **Aplicação em containers:** PostgreSQL, backend e frontend no `compose.yaml`, com healthchecks, arranque ordenado e os dados num volume persistente. O frontend fica em http://localhost:8000.
- **Imagens Docker** multi-stage, sem credenciais, a correr com utilizadores sem privilégios.
- **CI no GitHub Actions** em cada pull request e push para o `main`: 107 testes do backend, 32 do frontend, o teste E2E, Trivy (repositório e imagens) e SonarQube Cloud. As imagens só se constroem depois das verificações.
- **Imagens no Docker Hub:** `marrike/matriz-backend:0.5.0` e `marrike/matriz-frontend:0.5.0` (e `latest`), publicadas pela CI na tag `v0.5.0`, depois de todas as verificações e da análise do Trivy.
- **Documentação:** README revisto, plano de entrega e diagramas da execução e da pipeline.

## Correções de segurança

- Dependências do backend atualizadas para versões sem vulnerabilidades HIGH/CRITICAL conhecidas: Tomcat 10.1.61, Jackson 2.21.8 e driver PostgreSQL 42.7.14.
- Imagem do frontend em nginx 1.30 (Alpine 3.24), com os pacotes do sistema atualizados na build.

## Alterações que pedem atenção ao atualizar

| O quê | O que fazer |
|-------|-------------|
| `docker-compose.yml` passou a `compose.yaml` | Nada: os comandos `docker compose` encontram o ficheiro novo e o volume `matriz-dados` mantém-se. |
| `docker compose up -d` arranca agora a aplicação completa | Para desenvolver como antes (backend e frontend fora do Docker), usa `docker compose up -d postgres`. |
| `.env` | Acrescenta `http://localhost:8000` a `MATRIZ_CORS_ORIGENS`, e opcionalmente `MATRIZ_FRONTEND_PORTA` e `VITE_API_URL` (ver `.env.example`). |
| Portas | O backend em Docker e o `./mvnw spring-boot:run` usam os dois a 8080: não os corras ao mesmo tempo. |

## Verificação

- CI verde no PR #19 (run [43855997127](https://github.com/mariohenriquep/matriz-api/actions/runs/43855997127)) e falha controlada confirmada (run [43856714001](https://github.com/mariohenriquep/matriz-api/actions/runs/43856714001): o job do frontend falhou e o das imagens não correu).
- Aplicação em Compose validada no browser: login, abrir um projeto, criar uma tarefa e mantê-la depois de recriar os containers.
- A validação final, seguindo o README do zero, fica no relatório do Ex. 6.

## Limitações conhecidas

- O `VITE_API_URL` fica fixado na imagem do frontend: para outro endereço da API é preciso reconstruir a imagem.
- O quality gate do SonarQube exige 80% de cobertura no código novo, mas a pipeline ainda não envia relatórios de cobertura (JaCoCo, Vitest).
- Duas vulnerabilidades do `spring-webmvc` só têm correção no Spring Framework 7 (Spring Boot 4); estão aceites em `.trivyignore` porque afetam partes que a Matriz não usa.
- A imagem publicada do frontend chama a API em `http://localhost:8080/api/v1`.
- Continuam registados, sem correção por decisão da Ficha 04: SEC-03 (token no `sessionStorage`, sem CSP), SEC-04 (risco RK-02 aceite) e CR-04 (ver [`docs/quality-security-review.md`](../quality-security-review.md)).
